# Архитектура ai-trns

ai-trns — сервис распознавания речи: аудио → слова с таймкодами → SRT / txt. Плюс инструменты поверх
распознавания из stt-api: спикеры (`/diarize`), сравнение текста с аудио (`/tadiff`, `/docdiff`), проверка качества (`/review`).
Состоит из API-сервера (без GPU) и GPU-воркеров. Документ описывает, как они связаны,
где лежит код и где что развёрнуто.

Состояние на 2026-10-20, ветка `rest-api` (в master не влита).

## 1. Общая схема

```
 клиенты                                   GPU-хосты
 (ai-tools, скрипты)

        │ HTTPS/HTTP                              
        ▼                                         
 ┌──────────────────────────────┐   pull    ┌─────────────────────────────┐
 │ API-сервер  ai_trns/api      │◀──────────│ GPU-воркер  ai_trns/worker  │
 │  • задачи (SQLite), владельцы│  /worker/*│  • держит модель            │
 │  • авторизация: Keycloak +   │           │  • аренда задачи → аудио →  │
 │    ключи сервисов            │──────────▶│    распознавание →          │
 │  • хранение аудио/результатов│  задача,  │    words.json               │
 │  • рендер words → srt/txt    │  аудио    │  • heartbeat: прогресс,     │
 │  • TTL, повтор при сбое      │           │    продление аренды, отмена │
 │  GPU не использует           │           │  один воркер = один GPU     │
 └──────────────────────────────┘           └─────────────────────────────┘
```

**Принцип:** медленное и дорогое (GPU) отделено от быстрого и дешёвого (CPU).
- GPU-часть: аудио → **документ со словами** (`words.json`).
- Всё остальное делает API: SRT, txt, RTL-маркеры, хранение, доступ.

Поэтому формат или вид субтитров можно получить заново без повторного распознавания.

```
    cues.py                слова → реплики → SRT (алгоритм whisper_trainer, перенесён 1:1)
    subtitles.py           слова → txt / srt / json, RTL-маркеры для иврита
    textdiff.py            текст ↔ услышанные слова: removed / added / changed (/tadiff, /docdiff)
    diarize/               спикеры: engine.py — движок воркера (pyannote, MMS-CTC); srt, mapping,
                           resegment, labels — без моделей
    audio.py               ffprobe / ffmpeg: длительность, конвертация, декодирование в массив
    live/                  потоковое распознавание (движок воркера live): stream.py — LocalAgreement поверх

    api/                   API-сервер (FastAPI), без GPU

      auth.py              авторизация: токены Keycloak, ключи сервисов, владельцы задач
      jobs.py              хранилище задач (SQLite): очередь, аренда, истечение, TTL
      review.py            проверка качества STT людьми (/review/*, перенесено из stt-api)
      tadiff.py, diarize.py  /tadiff, /docdiff, /diarize (перенесено из stt-api): создают задачи
      live.py              /live: задача вида live, её события по SSE, стоп (TASK-live-transcription.md)
      results.py           виды задач: форматы результата и их рендер, счётчики
      submit.py            создание задачи из файла / URL и входов вида задачи
      docx_marks.py        текст из .docx и подсветка слов (/docdiff)
      config.py            настройки из окружения (AI_TRNS_*)
    paragraphs/            абзацы урока (TASK-speakers-paragraphs.md): build.py — реплики спикеров, абзацы Рава, чтец
                           (CPU); client.py — вызов сервиса абзацев из diarize-воркера; service.py — сам сервис
                           (mdb-lora на stt); evaluate.py — замер против отредактированной расшифровки
    worker/                GPU-воркер
      __main__.py          цикл: аренда → аудио → распознавание → результат; кэш моделей
      client.py            HTTP-клиент к API (только стандартная библиотека)
      config.py            настройки воркера
  scripts/                 запуск и деплой: run_api.sh, run_worker.sh, systemd-юниты, примеры env
  tests/                   pytest: реплики, слова, API, авторизация, воркер против настоящего API
  docs/ARCHITECTURE.md     этот файл
```

**Что импортирует что.**
- API не импортирует faster-whisper.
- Воркер не импортирует fastapi.
- Общие `protocol.py`, `words.py`, `audio.py` и модели-независимые части `diarize/`.

Поэтому у них разные зависимости: `requirements-api.txt` и `requirements-worker.txt`. Движку diarize нужен ещё
`requirements-diarize.txt` (torch, pyannote, torchaudio, uroman); он включается только там, где задан.

**Почему один репозиторий.** Контракт (`words.py`, `protocol.py`) общий для обеих частей, и его версии не должны разъехаться. На все машины ставится один и тот же коммит. Если версии протокола у воркера и API не совпадают, API отвечает воркеру 409.

## 3. Жизненный цикл задачи

```
клиент              API                                  воркер
 POST /jobs ───────▶ queued (аудио сохранено или URL)
                     ◀──────── POST /worker/lease  {worker, langs}
                     running, аренда 120 с ───────────▶ {id, params, source}
                     ◀──────── GET  /worker/jobs/{id}/audio   (если файл загружен)
                     ◀──────── POST …/heartbeat  каждые 5 с  {stage, progress}
                     ───────▶  {cancel: false|true}           (так доходит отмена)
                     ◀──────── PUT  …/result  words.json
                     done; рендер srt/txt; аудио удалено
 GET /jobs/{id} ───▶ done
 GET …/result ─────▶ srt / txt / json
```

- **Аренда.** Пока воркер шлёт heartbeat, задача его. Если воркер замолчал (упал, перезагрузка, сеть), аренда истекает, и задача возвращается в очередь. После `AI_TRNS_MAX_ATTEMPTS` (3) таких потерь задача помечается `error`.
- **Отмена.** `DELETE /jobs/{id}` сразу ставит задаче статус `cancelled`. Воркер узнаёт об этом на следующем heartbeat и прерывается между сегментами. Если он всё же пришлёт результат, получит 409.
- **Балансировка.** Отдельного балансировщика нет и не нужно. Воркер берёт задачу только когда свободен и только на тех языках, модели которых у него есть. Добавить мощность — значит запустить ещё один воркер с ключом.
- **Параллельность.** Одна задача на GPU. Две задачи на одном GPU не ускоряют работу: узкое место — CPU (VAD, спектрограммы), а не GPU.

## 4. Документ со словами (`words.json`)

Граница между распознаванием и всем остальным (`ai_trns/words.py`):

```json
{
  "version": 1,
  "duration_s": 6335.58,
  "language": "he",
  "model": "whisper-large-v3-turbo-hebrew-kabbalah-ct2",
  "timing": {"source": "engine_words", "boundary_correction_s": {"start": -0.1002, "end": 0.2197}},
  "text": "שלום, אנחנו קוראים ...",
  "segments": [{"start_s": 0.27, "end_s": 9.4, "text": "..."}],
  "words": [{"word": "שלום,", "start_s": 0.37, "end_s": 0.69, "probability": 0.98,
             "interpolated": false, "segment": 0}]
}
```

- **Таймкоды слов** даёт сама модель (word timestamps faster-whisper), без поправок.
- **Слова с гершаимом** (`לחו"ל`) модель режет на части, они склеиваются обратно.
- **Сегмент без пригодных таймкодов** получает время, распределённое пропорционально длине слов (`interpolated: true`).
- **Поправка границ** откалибрована whisper_trainer по профессиональным субтитрам архива. Она относится к модели и хранится рядом с ней (`ai_trns_model.json`). Применяет её не воркер, а сборщик реплик: если сдвинуть каждое слово, изменятся паузы, по которым режутся реплики.
- **Инвариант:** слова, соединённые пробелами, дают ровно текст транскрипта.

## 5. Субтитры (`ai_trns/cues.py`, `subtitles.py`)

Единственный вариант SRT — алгоритм whisper_trainer (`timing_alignment.py` @29645c8), перенесённый без изменений логики. Его параметры (`HOUSE_POLICY`) взяты из bundle v16:

| Параметр | Значение |
|---|---|
| Длина реплики | ≤ 84 символа, 2 сбалансированные строки по ≤ 32 |
| Длительность | ≤ 7 с |
| Разрыв | пауза > 2 с; после `.,?!:;`, если в реплике ≥ 22 символа |
| При переполнении | резать по самой длинной паузе, если до неё ≥ 10 символов |
| Тайминг | без наложений, обрезка по длительности аудио, кратность 1 мс |

Проверка целостности: текст реплик обязан совпадать со словами, иначе ошибка.

`fix_rtl` — RTL-маркеры поверх SRT, только для иврита. ai-tools включает его для `he`.

Старые варианты (`ToSubs` / `--impl 2` и разбивка по длительности / `--impl 1`) удалены.

**Сравнение с прод-сервисом whisper_trainer** на уроке 105 мин:
- разбивка совпадает: 713 реплик с одинаковым текстом, раскладка строк у всех 713 та же;
- расхождение времени начала реплики: медиана 20 мс.

Разница идёт от распознавания, а не от SRT: у них другой декодер и дополнительные шаги, см. раздел 8.

## 6. Модели и распознавание (`ai_trns/transcriber.py`)

- **Модели** лежат в `models/<lang>/` в формате CTranslate2. `auto` использует `models/en`.
- **Иврит** — [`orendar/whisper-large-v3-turbo-hebrew-kabbalah-ct2`](https://huggingface.co/orendar/whisper-large-v3-turbo-hebrew-kabbalah-ct2): веса прод-модели whisper_trainer, сконвертированные для обычного faster-whisper. Тот же файл (md5 `1ab3aa2d…`) уже лежит в текущем проде exec-api.
- **`ai_trns_model.json`** рядом с моделью задаёт её профиль и поправку таймкодов:
  ```json
  {"name": "...", "profile": "served", "boundary_correction_s": {"start": -0.1002, "end": 0.2197}}
  ```
- **Профили декодирования:**
  - `served` — пакетные VAD-окна, greedy, без prompt'а предыдущего текста; это рекомендация автора модели;
  - `stable` — beam 8, без VAD;
  - `fast` — beam 3, VAD.
- **Декодирование аудио** всегда через ffmpeg в массив. PyAV не используется: faster-whisper 1.2.1 несовместим с PyAV ≥ 15.
- **CUDA.** ctranslate2 4.8.3 нужен CUDA 12 (cuBLAS, cuDNN 9). Библиотеки ставятся pip-пакетами `nvidia-*-cu12`, `run_worker.sh` добавляет их в `LD_LIBRARY_PATH`. Поэтому версия CUDA toolkit на хосте не важна.
- **Выгрузка модели.** Воркер грузит модель под задачу (около 1 с) и выгружает её после `AI_TRNS_IDLE_UNLOAD_S` (300 с) простоя, потому что GPU делят с другими сервисами.

| GPU | Скорость (иврит, fp16, пачка 8) | Пик памяти GPU |
|---|---|---|
| RTX 3070 (`stt`) | ~125× реального времени (105 мин за ~50 с) | 3.4 ГБ (пачка 32 — 6.7 ГБ, почти не быстрее) |
| RTX 2080 (`ai-tools`) | ~95× (41 мин за ~26 с) | ~2–3.5 ГБ |

### Распознавание сервисом whisper_trainer (`ai_trns/stt_service.py`)

Временно, пока свой движок whisper_trainer не собран (раздел 8), транскрипт берётся у их прод-сервиса
`http://10.66.1.53:8765` (`transcription_service.py`), а не у модели на воркере. С ai-tools он доступен напрямую,
без Angie и ключа. Включается настройкой воркера `AI_TRNS_STT_URL`.

- Воркер не качает и не декодирует аудио: отдаёт сервису URL задачи и ждёт его SRT. Diarize по-прежнему идёт на своём GPU.
- Сервис принимает только URL и только иврит. Загруженные файлы и другие языки (`en`, `ru`, `auto`) воркер
  распознаёт своей моделью `models/<lang>` (`by_service()` в `worker/__main__.py`). Если моделей на воркере нет —
  API не принимает файлы для transcribe / tadiff / docdiff (`AI_TRNS_TRANSCRIBE_UPLOADS=0`, по умолчанию).
  На `ai-tools` (2026-11-04): модели `he`, `en`, `ru` (взяты из exec-api), `AI_TRNS_TRANSCRIBE_UPLOADS=1`.
- SRT сервиса хранится в документе (`"srt"`) и отдаётся без изменений; `cues.py` его не пересобирает.
  Слов с таймкодами сервис не даёт: время каждого слова раскладывается внутри его реплики (`interpolated: true`,
  `timing.source = "service_cues"`). Для txt и tadiff/docdiff этого хватает, таймкоды слов грубее.
- `model` в документе — `whisper_trainer@<sha bundle>` из `/health` сервиса.
- Прогресса внутри файла сервис не сообщает: стадии `queued_upstream` → `transcribing`. Отменить задачу
  у сервиса нельзя, воркер просто перестаёт ждать.

## 7. Авторизация (`ai_trns/api/auth.py`)

| Кто | Как | Что видит |
|---|---|---|
| Пользователь (ai-tools) | `Authorization: Bearer <токен Keycloak>`. Проверяются подпись (ключи `accounts.kab.info`, realm `main`), срок, издатель, клиент `azp=ai-tools`, роль `bb_user` | Только свои задачи (чужие отвечают 404). Все задачи — с ролью `AI_TRNS_ADMIN_ROLE` |
| Сервис / скрипт | `X-API-Key: <ключ>` или `Bearer <ключ>`. Ключи именованные: `AI_TRNS_API_KEYS=name:key,...` | Все задачи |
| GPU-воркер | `X-Worker-Key` + `X-Worker-Protocol` | Только `/worker/*` |

У задачи записывается владелец: `user:<sub>` или `key:<name>`. CORS открыт для `https://ai-tools.kab.info`.

## 8. Связь с whisper_trainer и stt-api

**whisper_trainer** (github.com/orendar/whisper_trainer) — дообучение модели, оценка качества и собственный прод-сервис распознавания `transcription_service.py` на 10.66.1.53:8765. Это и есть «upstream», к которому сейчас проксирует stt-api.

Что взято в ai-trns:
- веса модели — через Hub;
- алгоритм реплик и SRT (`cues.py`);
- склейка слов с гершаимом и интерполяция (`words.py`);
- калиброванная поправка таймкодов.

Что **не** взято: их конвейер вокруг распознавания —
- bundle v16 с проверками;
- энкодер на torch и форк CTranslate2 (decoder-only);
- VAD-guard и повторное декодирование краёв окон;
- ремонт и карантин галлюцинаций;
- языковой гейт и гейт пения;
- пакетная обработка (`bulk_inference`).

Из-за этого текст расходится с их продом примерно на 4% слов.

План: подключить их конвейер как ещё один движок воркера, без копирования кода. Воркер запускается их Python из их окружения (поэтому HTTP-клиент воркера написан только на стандартной библиотеке), вызывает `ResidentInferenceRuntime` и из их `words.jsonl` + `run.json` собирает наш `words.json`. API этого не заметит. Нужны bundle v16 от автора и сборка их форка CTranslate2 под целевую ОС.

Чем их сервис отличается от нашей схемы:
- **Связь с GPU:** у них всё на одной машине, драйвер сам раздаёт работу (push) дочерним процессам по одному на GPU. У нас API и воркеры разделены, воркеры забирают задачи сами (pull).
- **Хранение:** у них задачи только в памяти, результаты без очистки. У нас SQLite и TTL.
- **Доступ:** у них нет авторизации. У нас есть.
- **Выход:** у них только SRT/txt. У нас `words.json`, из которого рендерится остальное.

Из их схемы стоит взять: watchdog (900 с + 0.5 × длительность аудио) и переиспользование результата по хешу URL.

**stt-api** (`~/projects/stt-api`, был на хосте `stt`; **удалён 2026-11-04**, бэкап — `TASK-cleanup-old.md`):
- `/stt/*` — прокси на Whisper-сервис whisper_trainer (через Angie `/whisper/`). Больше не нужен: страница תמלול в ai-tools ходит прямо в `/jobs` ai-trns;
- `/review/*` — перенесено в ai-trns (`ai_trns/api/review.py`), см. ниже;
- `/diarize`, `/tadiff`, `/docdiff` — перенесено в ai-trns, см. ниже. В UI ai-tools ходят в ai-trns, страницы выключены в меню.

### Виды задач: `/tadiff`, `/docdiff`, `/diarize`

Пути и поля запросов те же, что в stt-api. Главное отличие: **ответ не сразу**. GPU на API нет, поэтому запрос
создаёт задачу (202, как `POST /jobs`), результат — `GET /jobs/{id}/result`. Счётчики (бывшие заголовки
`X-Docdiff-*`, `X-Diarize-*`) — в поле `stats` задачи и в тех же заголовках ответа с результатом.
Аудио — файлом (`audio`) или ссылкой (`url`, те же разрешённые хосты, что у `/jobs`).

| Вид (`params.kind`) | Движок воркера | Создаёт | Результат (первый — по умолчанию) |
|---|---|---|---|
| `transcribe` | transcribe | `POST /jobs` | txt, srt, json |
| `tadiff` | transcribe | `POST /tadiff/compare` (аудио + `text`) | diff (JSON stt-api), txt, srt, json |
| `docdiff` | transcribe | `POST /docdiff/compare` (`.docx` + аудио) | docx (`<имя>_marked.docx`), diff, txt, srt, json |
| `diarize` | diarize | `POST /diarize/srt`, `/diarize/words` (аудио + SRT + образцы голоса) | srt (размеченный), json (слова со спикерами) |

Сразу, без задачи и GPU: `POST /tadiff/compare-timestamps` (текст + слова с таймкодами) и `POST /diarize/words/srt`
(слова со спикерами → новый SRT).

- **tadiff / docdiff** — это обычное распознавание. Воркер не знает, что это сравнение. Когда приходят слова,
  API сравнивает их с текстом (`textdiff.py`, логика stt-api без изменений). В stt-api для этого был отдельный
  Whisper (transformers, `whisper-prev`) + CTC-выравнивание; здесь та же модель, что для субтитров, и её
  собственные таймкоды слов. Поэтому диффы с stt-api могут отличаться там, где модели слышат по-разному.
- **diarize** — свой движок воркера (`diarize/engine.py`, код stt-api): pyannote на весь файл, образцы голоса
  (`AI_TRNS_SPEAKERS_DIR/<Имя>/*.mp3`, на воркере, плюс присланные с запросом), каждое слово каждой реплики
  выравнивается MMS-CTC (запасной вариант — VAD из faster-whisper вместо torch.hub). Воркер возвращает документ
  со словами и спикерами (формат `/diarize/words` stt-api), а размеченный SRT строит API. Реплики и образцы
  воркер скачивает через `GET /worker/jobs/{id}/files/{name}`.
  Проверено на `stt` (RTX 3070) на уроке 1:45 ч: 159 с, результат совпадает с stt-api слово в слово
  (7790 слов, спикеры и таймкоды).
- **Воркер с diarize:** `AI_TRNS_WORKER_ENGINES=transcribe,diarize`, `HF_TOKEN` (лицензия
  `pyannote/speaker-diarization-community-1` принята), `pip install -r requirements-diarize.txt`. Без этого воркер
  берёт только распознавание, задачи diarize ждут в очереди. Модели одна за раз: при смене вида задачи
  предыдущая выгружается.
- **Абзацы и метки `הרב` / `קריין` / `תלמיד`** (`ai_trns/paragraphs`): diarize-задача с `paragraphs=true` после диаризации
  отдаёт текст реплик Рава сервису абзацев (`AI_TRNS_PARAGRAPHS_URL`, mdb-lora на `stt`, `ai-trns-paragraphs`) и кладёт в
  документ `paragraph_starts` (индексы слов). `?format=paragraphs` строит API: новый абзац на каждой смене спикера и там, где
  его ставит модель; чтец — голос, объявляющий чтение, иначе по тексту источника (`source=` .txt/.docx). Сервис недоступен —
  задача всё равно `done`, причина в `stats.paragraphs_error`, абзацы = реплики.

### Проверка качества STT (`/review/*`)

Те же пути и форматы, что в stt-api, и те же JSON-файлы (`AI_TRNS_REVIEW_DIR`): данные stt-api (`data/review`) можно просто скопировать.

Отличия от stt-api:
- **Распознаёт сервер.** Добавление урока создаёт обычную задачу ai-trns (`he`, `json`) с CDN-адресом аудио, урок хранит `job_id`. Когда задача готова, из слов строятся реплики (те же, что в SRT), урок становится `ready` с моделью из `words.json`. Ошибка задачи → `failed`, урок можно добавить заново. Браузер больше не распознаёт и не загружает транскрипт (`PUT .../transcript` удалён).
- **Синхронизация.** Состояние уроков обновляется при каждом чтении набора и в фоновом цикле API, до того как TTL удалит задачу.
- **Авторизация.** Нужен токен или ключ. Пользователь всегда действует от своего `sub`: чужой `reviewer` в пути или теле — 403. Сервисный ключ может указать любого рецензента. Отчёт (`/results`) доступен любому вошедшему.
- **Удаление** урока отменяет его задачу, если она ещё идёт.
- **Модель набора** — `AI_TRNS_REVIEW_MODEL` или модель последнего распознанного урока.
- **Baseline** (вторая модель для сравнения) не распознаётся. Старые `baseline_*` в данных сохраняются, рецензентам не показываются.

## 10. Решения и почему

| Решение | Почему |
|---|---|
| API и GPU раздельно | API может жить на машине без GPU, GPU-хостов может быть несколько, модель не мешает API |
| Воркер забирает задачи сам (pull) | Воркеру нужен только исходящий HTTP. Балансировка получается сама собой. Упавший воркер не теряет задачу (аренда) |
| Граница — документ со словами | SRT/txt и любые будущие форматы (спикеры, review) строятся без GPU. Движок распознавания можно менять, не трогая API |
| Поправка таймкодов в реплики, а не в слова | Сдвиг слов изменил бы паузы, по которым режутся реплики, и результат перестал бы совпадать с whisper_trainer |
| Один алгоритм SRT (whisper_trainer) | Откалиброван по профессиональным субтитрам архива. Старые варианты были хуже и с багами (`ToSubs` терял последнее слово) |
| Код whisper_trainer не копировать, а вызывать | Их декодер активно развивается, и их оценка качества должна видеть ровно прод-код. Копия разошлась бы |
| tadiff / docdiff — распознавание + сравнение на API | Второй Whisper на GPU не нужен, сравнение дешёвое и повторяемое из слов |
| diarize — отдельный движок, SRT на API | pyannote и MMS тяжёлые и нужны не на каждом GPU; документ со словами и спикерами позволяет перестроить SRT без GPU |
| HTTP-клиент воркера только на stdlib | Воркер можно запустить внутри locked-окружения whisper_trainer, не добавляя туда пакеты |
| Модель выгружается при простое | GPU 8 ГБ делят воркеры ai-trns (live, transcribe, diarize) и ollama. Загрузка занимает около 1 с |
| Одна задача на GPU | Две задачи на одном GPU не ускоряют работу: узкое место — CPU |
| Пакет `ai_trns/` внутри репо | Запуск `python -m ai_trns.api` и `python -m ai_trns.worker` из любой папки, нет конфликтов имён (`config`, `audio`) |
