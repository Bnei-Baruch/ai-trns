# Задача: потоковая транскрипция для live

Черновик, 2026-10-20. Сейчас ai-trns умеет только файлы: задача → очередь → воркер распознаёт целиком → результат.
Для live нужен текст с задержкой в секунды, пока трансляция идёт.

## Что нужно решить до работы
1. **Источник звука — WebRTC, медиасервер Janus** (решено 2026-10-20). Осталось уточнить:
   - хост(ы) Janus и версия (0.x или 1.x — у них разный формат `rtp_forward`);
   - плагин и что именно слушаем: `videoroom` (звук одного выступающего, `publisher_id`), `audiobridge` (микс комнаты)
     или `streaming` (готовая точка вещания);
   - номер комнаты / id точки, `admin_key` или `secret` комнаты (нужны для `rtp_forward`, если включён
     `lock_rtp_forward`);
   - адрес Janus API (HTTP `/janus` или WebSocket) — доступен ли с API-сервера / GPU-хоста;
   - проходит ли UDP от Janus до GPU-хоста (`ai-tools`, `stt`).
2. **Кто смотрит результат.** Страница в ai-tools, оверлей субтитров на трансляции, сохранение в архив?
3. **Задержка.** Сколько допустимо: 2–3 с (частичные гипотезы, потом исправления) или 5–10 с (только готовые фразы).
4. **Сколько потоков одновременно** и какие языки (только `he`?).
5. **GPU.** На время трансляции GPU занят постоянно. Какой хост: `ai-tools` (RTX 2080, рядом exec-api и ollama)
   или `stt` (RTX 3070, но `stt → ai-tools` закрыто).

## Схема (предложение)

```
 медиасервер WebRTC                API ai-trns                        клиенты
     │  Opus (WebRTC или RTP)           ▲                              (ai-tools)
     ▼                                  │ WebSocket (исходящий       ▲
 live-воркер ──────────────────────────┘  от воркера)                │ WebSocket / SSE
  • Opus → PCM 16 кГц                     • сессия live: владелец,    │
  • VAD + скользящее окно                   статус, подписчики ───────┘
  • частичные / готовые фразы             • в конце — обычная задача (srt/txt/json)
  • в конце — words.json
```

### Как воркер получает звук: Janus `rtp_forward`

Janus сам пересылает аудиодорожку голым RTP (Opus) на UDP-порт воркера. WebRTC, ICE и DTLS в воркере не нужны.

```
воркер / API ──(Janus API: attach плагин, rtp_forward)──▶ Janus
Janus ──(RTP Opus, UDP → host:port воркера)──▶ ffmpeg -protocol_whitelist file,udp,rtp -i live.sdp → PCM 16 кГц
```

- Включение: запрос `rtp_forward` в плагине (`videoroom` / `audiobridge`) с `room`, `publisher_id` (для videoroom),
  `host`, портом и `admin_key`/`secret`. В ответе `stream_id`; остановка — `stop_rtp_forward`. В Janus 1.x для
  videoroom порты задаются в `streams: [{mid, host, port}]`, в 0.x — `audio_port`.
- SDP-файл для ffmpeg: `m=audio <port> RTP/AVP <pt>` + `a=rtpmap:<pt> opus/48000/2`. Payload type взять из ответа
  или задать в запросе.
- Пересылка живёт, пока жив издатель: выступающий переподключился → новый `publisher_id` → пересылку создать заново.
  Следить через события плагина (`publishers` / `leaving`) или проверять `listforwarders` раз в несколько секунд.
- Если Janus и воркер в разных сетях — `srtp_suite` / `srtp_crypto` в запросе (ffmpeg умеет SRTP).
- Кто вызывает Janus API: проще воркер (он знает свой host:port). Если Janus API с GPU-хоста недоступен — API ai-trns,
  передав воркеру порт.

**Запасной вариант**, если `rtp_forward` закрыт или UDP до GPU-хоста не пройдёт: воркер подключается к Janus
как обычный WebRTC-подписчик (`aiortc`, signaling Janus по HTTP/WebSocket, ICE через TURN). Приём звука — отдельным
процессом, который отдаёт PCM в pipe: `aiortc` тянет PyAV, а он конфликтует с faster-whisper 1.2.1.

- API звук не видит, только управляет сессией и раздаёт текст.
- Воркер с API связан только исходящими соединениями (как pull сейчас): открывает WebSocket к API. Так же будет
  работать и с `stt` через Angie.

**2026-10-22: источник — HLS трансляции, не WebRTC.** Плеер kli.one играет `https://edge3.uk.kab.tv/live/heb-medium/playlist.m3u8`
(в браузере это `blob:` MediaSource — с сервера его не прочитать). ffmpeg на воркере читает HLS сам, Janus не нужен;
пункты про Janus ниже — на случай, если понадобится другой источник.

## Ограничения и риски
- **Модель whisper_trainer не потоковая.** Окно + повторное декодирование даёт качество хуже, чем распознавание
  файла целиком; финальный SRT лучше пересчитать по записи обычной задачей после трансляции.
- **Сервис whisper_trainer (10.66.1.53:8765)** принимает только URL файлов, потоков нет — live только на своём движке
  (faster-whisper, та же модель).
- **GPU 8 ГБ делится** с exec-api / ollama / пакетными задачами: на время трансляции пакетные задачи на этом GPU встают.
- **Повторное декодирование** каждые ~1 с окна в 10–30 с — постоянная нагрузка, а не 95× реального времени, как у файлов.

- **Потери пакетов** — RTP по UDP без повторов: мелкие потери Opus маскирует, длинные дают пропуски текста.
  Между площадками может понадобиться запасной вариант через WebRTC/TURN.
- **Нагрузка на Janus:** каждая пересылка — ещё одна копия потока; для одного звука (~50 кбит/с) несущественно.

## Проверка (готово, когда)
- Ручная проверка канала: `rtp_forward` тестовой комнаты на GPU-хост, `ffmpeg -i live.sdp out.wav` пишет звук.
- Запуск live на тестовой комнате Janus → в клиенте текст с задержкой не больше оговорённой.
- Обрыв воркера → сессия продолжается на другом воркере или `error`, клиент это видит.
- Стоп → задача `done`, SRT скачивается, текст совпадает с тем, что показывался как `final`.
- Пакетные задачи на другом воркере идут параллельно.
